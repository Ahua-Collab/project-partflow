# 阶梯工坊 · Stepwise

[English](README.en.md) · 中文

**面向非专业开发者与独立开发者的 Codex 分段协作开发工作流，可按需自行适配其他 AI 工具。** 从一个想法开始，把工作拆成可检查的小段，留下能交接、能恢复、能验收的记录。

“阶梯工坊 · Stepwise”是展示名；仓库目录与技能名继续使用 `project-partflow`，调用方式仍是 **`$project-partflow`**，不影响原有项目和安装路径。

原生面向 Codex 使用。适配其他 AI 工具时，需要使用者自行调整工具接口、角色派工和文件权限，并验证实际行为；本包未验证其他 AI 工具的现成兼容性。

把软件想法变成可验收的项目书，再按模块分工、按 Part 派工与独立审核。项目进度与证据保存在磁盘上，方便中断恢复、角色交接和换设备继续。

**Part 是有独立验收门禁的工作单元，不是一天。** 一个 Part 可以跨多天；补正仍属于原 Part。技能组织协作与验收，具体算法、局部结构和调试方法由任务执行者在范围内决定。

```text
需求 → 项目书与所有权 → 当前 Part 正式任务 → 实现与交付
                                               ↓
下一 Part ← 整个 Part PASS ← 主线复验 ← 独立审核
                                               ↓ 未通过
                                          原 Part 补正
最后一个 Part → READY_FOR_ACCEPTANCE → 产品验收与用户确认 → COMPLETE
```

## 适用场景

不必先学会写详细技术提示词。你可以先用日常语言描述想做什么、给谁用、怎样算完成，让总控帮助整理需求和待决定的问题。

| 你遇到的困难 | 阶梯工坊提供的便利 |
|---|---|
| 有想法，却不知道从哪里开始 | 先整理目标、最小可用范围和一段能验收的成果 |
| 一个人兼顾产品与开发，容易遗漏 | 把需求、模块责任、依赖和验收放进项目文件 |
| 多个 AI 任务说法不同，交接费力 | 使用正式任务、唯一文件所有者和稳定问题 ID |
| 对话中断、额度用尽或换设备 | 从磁盘记录和 Git 对账，减少靠记忆重建背景 |
| 不知道“测试通过”是否真的做完 | 区分交付、独立审核、主线验证和用户验收 |

这些便利来自明确的工作约定，不是经过量化验证的效率或费用承诺。产品取舍、必要判断与最终确认仍需要人参与；有工具和授权时可以自动执行相应步骤。

适合需要多个模块、明确责任、分段验收和长期恢复的软件项目。小项目可只有总控与一个实现角色；角色数和 Part 数按需求确定。普通单文件修改通常无需引入完整流程。

它提供的是 Markdown 规则、模板和可选本地检查器。它不会自行安装依赖、创建后台服务、获得系统权限或保证产品正确。角色任务的创建、发送及外部动作仍取决于宿主能力与用户授权。

## 安装

下载仓库完整目录或 ZIP，确保安装目录层级如下；不要只复制 `SKILL.md`，也不要形成双层 `project-partflow/project-partflow`。

```text
<Codex 技能目录>/project-partflow/
  SKILL.md
  INSTALL.md
  agents/openai.yaml
  references/
  assets/
  scripts/
  README.md
  docs/
```

使用当前设备配置的 Codex 技能目录：设置 `CODEX_HOME` 时为其下的 `skills/`，否则为用户目录下 `.codex/skills/`。同名技能已存在时先另存备份，再由用户选择替换，避免覆盖正在使用的版本。重新加载技能列表或新建会话后，确认“分段项目总控”可见。

本仓库根目录本身就是完整 skill。解压目录可能带分支后缀，安装时把实际 skill 目录命名为 `project-partflow`。源码、项目台账与技能分别保存；安装技能不会迁移项目。

详细说明见 [INSTALL.md](INSTALL.md)；初次使用见 [快速开始](docs/quickstart.md)。

English installation: [INSTALL.en.md](INSTALL.en.md). 原始技能规则与模板保留中文；英文文档解释同一用法，不另设一套门禁。

## 第一条指令

```text
请使用 $project-partflow。我想做一个离线资料整理工具，给个人使用，运行在我的电脑上。
请先澄清会改变方案的问题，形成项目书、模块所有权和可观察验收，再安排 Part。
当前对话作为总控。需要创建长期角色任务时先依据我的明确授权与宿主能力执行。
```

已有项目：

```text
请使用 $project-partflow 接手这个项目。先只读核对权威治理来源、项目书、AGENTS、
STATUS、上一个 Part 和当前任务的 prompt/review、开放问题与 Git。
报告已完成、在途、缺失和下一动作，保留旧记录；不要重新初始化项目或重复合入。
```

日常可说“继续当前 Part”“只审核这份交付”“按最新 review 继续补正”“换设备恢复”。具体短指令与完整周期见 [日常操作教程](docs/daily-workflow.md)。

## 已有机制

| 机制 | 怎样使用 |
|---|---|
| 唯一活动总控 | 负责治理、派工和独立验收；实现与测试交文件所有者 |
| 文件引用式交接 | 完整 prompt/交付/review 落盘；可共享文件时聊天传角色、任务、路径与结论 |
| 按需读取 | 每轮核对当前状态与相关依赖；更早历史按问题回溯；恢复与里程碑保留完整必读规则 |
| 保留模型发挥 | 硬性要求写目标、契约、范围、验收；实现建议明确可调整 |
| 同 Part 补正与 CR | 稳定问题 ID、追加 revision；跨模块变更交唯一所有者 |
| 主线门禁 | 送达、交付、技术接受、合入、最终 PASS 分别记录 |
| 证据约束 | 原文、代码支持、运行观察与推断分开；必需证据不足不放行 |
| 磁盘恢复 | 用项目文件与 Git 对账，不把旧聊天或旧角色树当作权威进度 |

这不是新增功能清单；规则原文见 [SKILL.md](SKILL.md) 和 [读取约定](references/context-budget.md)。现有项目更严格的治理仍有效。

## 工具与依赖

文本流程只需宿主能读取项目文件。可选检查器使用 **Node.js 与 Git**，无第三方 npm 包、无联网或账户需求。本次实际验证环境与结果见 [验证说明](docs/validation.md)；未建立其他版本的兼容承诺。

```text
node <技能目录>/scripts/self-test.mjs
node <技能目录>/scripts/gate.mjs inputs <权威治理根目录> <角色ID>
node <技能目录>/scripts/gate.mjs check <权威治理根目录>
node <技能目录>/scripts/gate.mjs ownership <项目根目录> <角色ID> <基线SHA> <交付SHA>
```

`inputs` 给路径/哈希索引，不证明文件已读或来源最新；`check` 检查状态结构与依赖；`ownership` 检查已提交 diff 的配置所有权，未提交内容与 prompt 更窄范围仍需人工审查。三者都不替代独立技术审核或产品测试。自测会在系统临时目录创建并清理合成 Git 仓库；其他三个命令只读项目。

模板中的角色、任务、SHA、路径与布尔值必须依据实际证据填写。空模板不能直接作为已通过项目运行 `check`。

## 许可与发布范围

本发布副本保留原技能文件，另加中文说明与匿名化教学。它不包含任何业务项目源码、真实行情、账户、凭据、聊天记录或私人工作日志。当前未附加新的许可证，也不替用户选择开源许可；如需授予复用许可，由权利人明确选择后补充。
