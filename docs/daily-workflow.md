# 日常操作教程

[English](daily-workflow.en.md) · [阶梯工坊 · Stepwise](../README.md)

“日常”指平常怎么使用，不按日期创建 Part。用户主要表达目标、转发短指令和提交交付，机器字段由总控按证据维护。

## 先找当前动作

| 看到什么 | 对总控说什么 | 应得到什么 |
|---|---|---|
| 只有想法 | 请先形成可验收项目书 | 目标、范围、角色、依赖、Part 与验收 |
| 当前 Part 尚未派工 | 请生成当前 Part 第一个可执行任务 | 已归档完整 prompt 与可用转发指令 |
| prompt 已存，无送达证据 | 核对是否送达，避免重复创建 | 真正回执或明确待转发 |
| 角色在途 | 核对现有任务并继续 | 实际进展、阻碍与下一步，保持原任务 |
| 有交付 | 只审核这份交付 | 独立 review，不自动派下一 Part |
| review 未通过 | 继续原 Part，逐问题补正 | 稳定问题 ID 与追加 revision |
| 技术通过，未合入 | 按已有授权集成并复验 | 源→主线映射和真实主线证据 |
| 本段任务都 PASS | 核对整个 Part 门禁 | 整段 review，满足条件后更新 STATUS |
| 会话中断或换设备 | 从权威磁盘与 Git 恢复 | 完成/在途/未知及唯一下一动作 |

## 一轮完整协作

总控先确定唯一文件所有者，把本任务的目标、硬性约束、允许路径与可观察验收写入 prompt；完整归档后发送。实现者读原文并核对基线，在范围内自行选择方法，连续完成实现、必要验证与修复；遇跨界依赖提最小 CR，继续不依赖它的工作。

实现者交完整报告，总控检查实际改动与完整关键路径，既看测试也看需求是否正确表达。必需证据缺失、失败或越界都不放行。需要补正时保留原问题 ID、原提交与原失败，追加编号说明；新问题另编号，避免把“改过了”当成“已关闭”。

技术接受后，按实际授权执行精确集成，核对是否已有等价提交，再运行必要的主线检查。审核与集成记录齐备才最终 PASS；一个角色 PASS 不代表本 Part 全部通过。

## 减少重复读取的正确用法

完整材料落盘一次；聊天只传结论、问题 ID、精确路径、提交和下一动作。总控每个新 Part 仍核对权威 STATUS、Git、治理版本、上个 Part 与本任务依赖；更早历史仅按当前问题回溯，不默认重讲全部 daily/prompt/review。

在同一任务当前上下文仍完整保有原文，且来源、角色、根目录相同并核对实际 SHA-256 未变时，可复用相应原文。新会话、压缩摘要、交接、换机、变化或不确定时重新读本角色必需原文；里程碑/最终验收完整重读治理。索引、文件时间或 HEAD 相同都不能证明已读或正文未变。项目更严时照原治理执行。

`inputs` 可定位相邻 Part 与角色文件，但不覆盖所有任务引用的契约、开放 CR 和证据；按 prompt 补齐。输出被截断时分段补读，不能把已显示部分当作全文。

## 保留模型的实现自主权

```text
验收：取消后不能报告成功；资源上限覆盖整次任务；结果能按固定输入复验。
范围：只改本模块与对应测试。跨公共接口先提出最小变更请求。
实现建议：可考虑分阶段处理；若更好的方案满足契约与验收，可自行调整并说明理由。
```

不要把每个算法步骤都写成硬命令。模板是信息覆盖提示；可以调整叙述和布局，但不能移除验收、责任、授权与证据边界，也不能破坏机器状态字段。

## 沟通时区分状态

“已归档”“已送达”“正在执行”“已交付”“技术接受”“已合入”“主线最终 PASS”是不同事实。聊天尽量写“谁、哪个任务、依据哪个文件/提交、实际做到哪、还缺什么”。角色空闲不是提前执行未来 Part 的理由。

## 恢复与收尾

换设备迁移项目源码、Git 历史、治理、prompt/review 与验收引用的脱敏证据；单独安装技能。工具路径、任务 ID、权限和工作树重新发现。先确认唯一活动总控，再接续；没有任务工具可以手动转发，不能把内部代理当作已创建的长期窗口。

最后一个 Part PASS 后记 `READY_FOR_ACCEPTANCE`。实际用户流程、安装运行、升级回退、已知限制和需求映射完成，再按用户确认或事先委托的客观验收方式记 `COMPLETE`。缺失证据继续列缺失，不补造历史成功。
