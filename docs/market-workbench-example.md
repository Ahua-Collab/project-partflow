# 行情研发示例：怎样推进而不反复绕圈

[English](market-workbench-example.en.md) · [阶梯工坊 · Stepwise](../README.md)

本页把 OKX 类盘口、采集和回放工具研发中的协作经验改写为**匿名教学案例**。模块、任务 ID、场景与数据均为教学设定，不复刻任何真实项目的配置、实现、交易数据或验收结果。本文说明如何使用流程；不提供当前交易所接口规格、账户操作或交易建议。

## 示例目标与角色

假设要做一个本地行情研究工具：从离线合成事件重建简化盘口，把确认写入的事件落盘，再查询和回放。第一阶段不联网、不接账户、不下单。产品需求用用户能观察的行为定义，例如乱序输入被标识、取消不会伪报成功、恢复后不重复计数。

| 角色 | 教学中的唯一职责 | 遇到跨界怎么办 |
|---|---|---|
| director | 项目书、派工、独立审核、主线门禁 | 把 CR 派给实际所有者 |
| contract | 公共事件契约、根构建与依赖 | 收到正式任务后修改共享部分 |
| ingest | 接收、校验、编排与回放 | 需要新存储 API 时提最小 CR |
| storage | 持久化、恢复与迁移 | 不替 ingest 修改消费者实现 |

这是示例分工；实际小项目可合并实现职责，仍保留独立审核。不要把这些角色数量和路径当成所有项目默认值。

## Part 规划示例

| Part | 结果 | 门禁例子 |
|---|---|---|
| 01 | 确定事件契约与离线输入 | 单位、身份、质量状态和失败语义一致 |
| 02 | 完成接收、确认写入与回放 | 合成输入→处理→持久化→查询闭环 |
| 03 | 完成取消、停止与跨进程恢复 | 未完成工作保留、真实回执、重复恢复幂等 |
| 最终验收 | 用户实际导入、运行与导出 | 安装运行、失败提示、限制和用户确认 |

公共契约应先于消费者通过；同 Part 中可以先做跨模块前置，再继续主体。计划表列出未来 Part 不等于允许提前执行。

## 一次补正怎样写清楚

假设 `INGEST-RECOVERY` 的交付报告说“程序退出了”，但未证明待处理派生工作可恢复。总控应分清四件事：进程停止、原始事件确认写入、派生任务完成、最终质量可用。若实现只验证其中一项，测试绿色也不能关闭整个需求。

补正保留 `INGEST-RECOVERY` 与问题 `REC-001`，写清原场景、期望不变量、精确证据、允许路径和关闭条件。先判断既有接口能否表达持久工作边界；确有缺口才提 CR 交 storage。旧模块 PASS 不回写为失败，新需求补正另归档；消费者等待前置最终主线通过后再限定导入并验证完整链路。

**经验分类：**“缺少持久工作边界”可能是实现或契约缺陷；“没有先归档正式任务”属于流程未落实；“权限不允许访问原数据”属于环境边界。不能因为都导致停在同一 Part 就认定 skill 的推进机制有问题。

## A/B 对照为何反复出错

在这里，A/B 指软件方案的受控性能对照。先固定输入集合、被测提交、构建类型、实际程序、配置、机器负载与统计起止点，再一次只改变有意义的变量。把“源数据就绪→实际处理”和“程序读到→实际处理”混为同一指标，会把等待移出统计而产生表面改善。

一个实验报告至少解释：验证什么假设、对照条件、实际改变什么、如何知道处理的是同一类输入、失败/取消是否仍正确、观察到什么、未知什么。若输入或调度不同，说明不可直接比较；不要报未经同条件验证的加速倍率。

失败后先读原件、最小路径和直接时序，证据不足才补有界见证。保留旧失败与准确统计，不循环完整测试直到偶然绿色。正常完成、正确保护早停、局部单测通过和完整容量达标分别报告。独立审核仍要检查测试期望是否和原需求一起写错。

## 避免测量争用和证据膨胀

独立模块的普通开发可在授权内并行；关键性能测量由总控协调窗口，独立构建输出隔离。共享 CPU 或磁盘争用会影响解释，不能把角色间干扰直接归为产品瓶颈。

完整日志和证据索引留在项目，聊天仅回结论与定位。已绑定且本次操作不触及的历史大样本无需每轮重新全量散列；当前可能被覆盖的输入、程序和固定输出仍须保护，最后提交绑定与必要独立验证不省略。哈希一致证明所查内容一致，不证明行为正确。

## 如何用于真实行情项目

先把真实项目自身的接口、数据授权、需求与当前状态写清楚，再套用上述协作方法。接公共行情、读私有账户、模拟操作、实盘、远程上传是不同边界，不能用本教学的离线研发范围互相替代。具体协议、地区可用性和账户权限应在实施时另行查证，不从匿名案例推断。

本页不声称真实项目目前存在上述旧缺陷，也不声称已经完成其代码审计、容量验证或收益验证。
