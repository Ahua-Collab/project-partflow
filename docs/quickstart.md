# 快速开始：先做成一小段可验收成果

[English](quickstart.en.md) · [阶梯工坊 · Stepwise](../README.md)

## 1. 确认安装完整

确认 `project-partflow/SKILL.md` 与 `references/`、`assets/`、`scripts/`、`agents/` 在同一技能目录。对话里明确调用 `$project-partflow`。若宿主不能识别技能，可直接提供已安装文件位置，由宿主按其能力读取；不要谎称已加载。

只运行文本流程不必安装 Node.js；只有需要脚本检查时才使用已有 Node.js 与 Git。没有工具时按相同规则人工核对，记录“人工核验”，不记脚本 PASS。

## 2. 描述想要的结果

给总控使用者、输入到输出的一次真实操作、目标设备、已有材料、不能做什么，以及怎样判断完成。没有偏好的技术不必硬选，让总控给有理由的方案和待验证假设。

```text
使用 $project-partflow，做一个离线笔记搜索工具。
我导入自己选择的文本文件，输入关键词后看到匹配段落与原文件位置。
只处理选定目录，不上传文件。先做小范围可用版，以可观察行为定义验收。
你作为总控先写项目书和所有权，具体实现方法交实现者决定。
```

总控输出可派工项目书：需求 ID、模块接口、唯一文件所有者、数据边界、连续 Part、里程碑与最终验收。可用 [项目书模板](../assets/PROJECT_PLAN.md) 起草，不能直接把样例当作用户已认可需求。

## 3. 建立本项目文件

新项目在认可范围内生成；已有项目先恢复，不覆盖原治理。

```text
PROJECT_PLAN.md               需求、所有权、排期与验收依据
AGENTS.md                     本项目的角色边界与读取规则
docs/privacy-boundaries.md    数据用途、外传和生命周期
.engineering/project.json    schema v2 计划与路径映射
.engineering/roles.md         角色定位、活动关系与送达回执
progress/README.md            记录约定
progress/STATUS.md            唯一进度入口
progress/Part-01/             本段 prompt、交付、review
```

总控按事实填好 `owners`、`tasks` 和依赖，模板不预填通过。主分支按现场 Git 确定，不强迫旧项目改名。Git 初始化和角色任务创建只在实际授权范围内执行。

## 4. 派当前 Part 的第一个任务

总控核对权威 STATUS、Git、治理版本与前置，先保存完整 prompt。它应说清可观察目标、精确可写范围、接口与失败边界、验收、交付位置；建议实现与硬性要求分开。

共享文件可读时，一条短转发即可：

```text
你是 builder，执行任务 BUILD-01。权威治理根为当前设备确认的项目主工作区。
先完整读取 progress/Part-01/prompt-builder-BUILD-01.md 及其中列出的原文，
核对实际基线与范围，再连续实现、必要验证、修复并交付。
```

这段是教学用语，不是给任何真实项目的执行授权。若接收者不能读共享文件，总控提供完整可复制 prompt，不要求用户自行拼接。

## 5. 交付后独立审核

实现者报告真实基线→最终提交、准确改动、必要验证与日志、未验证和跨界请求。总控阅读完整交付与实际 diff，按需求审核和必要独立复验。发现问题就追加原 Part 的 revision；技术接受后按授权集成并在实际主线复验。

只有本 Part 全部前置、主体和到期里程碑最终 PASS，才能写整个 Part review，再递增 STATUS。最后一个 Part 之后还需产品验收与用户确认。

## 6. 下次继续

```text
继续当前项目。先从磁盘与 Git 对账当前任务、未关闭问题和最近审核；
已完成的安装、派发与合入不要重复。继续授权内下一动作，遇真实边界时只暂停受影响部分。
```

不要每次重新粘贴整份项目书；也不能用摘要省掉恢复必读原文。两者的具体边界见 [读取约定](../references/context-budget.md)。
