## Every round rereads too much history

Check whether the project's AGENTS is stricter than the skill. Current rules read by role and stage, focusing on the previous Part, current task, and prerequisites; older history is traced when relevant. Keep complete reports on disk and hand off paths and issue IDs instead of repeatedly pasting governance.

Reuse still requires full originals in the current context, the same source, and verified unchanged hashes. New sessions, compression, and handoffs trigger mandatory reading; milestones and final acceptance reread governance fully. The skill has no token meter, persistent reading permit, or measured savings percentage.

## ��Done�� does not lead to the next step

State the task ID, formal prompt, actual baseline/final commit, delivery path, and exact stage. The coordinator separately checks dispatch, execution, delivery, technical acceptance, integration, and mainline PASS. A file, named window, or exited process does not alone prove business completion.

## Templates constrain implementation too much

Make contracts, compatibility, authorization, resources, and observable acceptance mandatory. Make algorithms and local organization adjustable suggestions unless correctness depends on sequence. Markdown layouts can change; state fields, ownership, independent review, and authorization boundaries remain.

## Green tests still miss a defect

Check expectations against the original requirement and inspect complete affected functions and callers. Use independent counterexamples when necessary: cancellation/state consistency, cross-loop budgets, real acknowledgments, time windows, edge cases, or repeated recovery. Do not simply rerun identical assertions or label a static concern as a reproduced failure.

## Repeated A/B or performance failures

Fix the hypothesis, commit, input, executable, configuration, timing boundary, and load. Inspect the failed evidence; repetition is not causal evidence. Prefer the smallest informative witness, then verify the affected matrix after relevant production changes. Do not merge different runs into an imaginary complete successful command. See the [market-data example](market-workbench-example.en.md); this is not a general statistical-testing framework.

## A dependency crosses modules

Normally keep the Part, write a minimal change request, name its owner, affected tasks, and deadline. Have that owner implement and pass independent review, integration, and mainline verification before the consumer imports it. Pause only dependent work, not unrelated authorized work, and do not start future Parts early.

## The checker rejects the project

| Error category | What to inspect |
|---|---|
| `schema v2 required` / `do not reset` | Legacy Day/schema 1; preserve history and recover manually rather than changing only the version |
| `fill project owners` / `fill planned tasks` | Unfilled templates; instantiate the approved plan first |
| `next_part` / `prefix` | Continuous completed indexes; do not manufacture success by editing progress |
| `not final PASS` / `no mainline verification` | Technical acceptance, missing mainline checks, or logs |
| `not integrated` / `missing commit` | Actual branch, Git objects, or incomplete migrated history |
| `overlapping ownership` | Exact files or trailing-`/` directory prefixes; no overlap or globs |
| `unsafe relative path` / `path escapes project` | Project-relative references and links that escape the project |
| `task started while issue blocks it` | `blocks` means immediate blocking; clarify actual scope without deleting the gate |
| `ENOENT` | Referenced instructions, reviews, or logs missing from the current project |

Rejection helps locate a problem. It does not authorize overwriting history, inventing logs, or reclassifying mandatory issues merely to pass. An `ok` result still needs technical review.

## Node, Git, or temporary-directory permissions are missing

Continue authorized text work and record automated checks as unexecuted or blocked. The self-test initializes synthetic Git repositories in a temporary directory; a sandbox may prohibit `.git/config` writes. Use the host's normal permission process or record manual checks. Do not disable protections or install unknown software.

## Missing role windows, IDs, or legacy records

Recover from files and Git, then rediscover available tools. If task creation is unavailable, provide complete manual instructions and record user-confirmed role titles without inventing IDs or receipts. Stop the old coordinator's dispatch before transferring active control.

Legacy `daily/Day-NN` names represent the same kind of logical work unit. Preserve numbering, failures, and accepted decisions. The v2 checker rejects legacy formats and does not migrate them automatically. Migrate references and verify history only when explicitly authorized; never clear the ledger to start over.

## When does the user need to decide?

Product choices, missing essential facts, unauthorized external actions, or host permissions may require a decision. Ordinary implementation, necessary checks, and in-scope fixes should not require step-by-step permission. Identify the exact rule and affected action when pausing, preserve a recovery point, and continue independent authorized work. Do not ask for an authorization already given.
