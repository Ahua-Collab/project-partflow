# 独立审核与最终交付

## 结论的证据边界

在既有验收表中把关键结论绑定到需求/问题 ID、原文或代码位置、版本/提交、实际验证结果；不另建重复台账。区分“原文规定”“代码支持”“实际运行观察”“推断/未验证”。检查器通过只说明它检查的结构关系成立，不能证明日志真实、功能正确或模型没有幻觉；审阅者须查看相关原文、实际 diff 和必要运行证据。

路径、符号、API、依赖版本先从仓库及匹配版本的官方资料核实；不凭相似名称或记忆补造。静态检查不能冒充运行结果，合成数据不能冒充真实场景，角色自报不能冒充独立验证。必需结论缺证据时标为未验证并阻断相关放行；非阻断项记录影响及到期点。不为满足模板伪造 SHA、日志、回执或 PASS。

## 证据先绑定到被审提交

核对原始及最新补正 prompt、完整提交链、实际文件范围、关键实现、公开接口、最终测试输出。记录源提交、工作树、构建目录、构建配置、测试程序来源、主线结果与执行环境。目录名相同、旧日志残留、旧可执行文件通过，都不能证明当前代码通过。编译失败后不能继续拿旧程序的绿色结果验收。

有增量构建风险时，用最小头文件/输入变更确认真实重编译与依赖追踪；问题未解决前可用干净独立构建检验当前实现，并把根构建缺陷转交所有者。不要把特定编译器、测试开关、日志文件名或固定全量测试数写成所有项目通用要求。每次验证选择与改动风险相称的矩阵；低风险补正没有改公共接口时无需机械重复所有昂贵探针。

日志使用最终运行结果，失败历史也保留其上下文。权限受限和正常权限下结果分开；只有实际得到授权并完成复跑，才能记录正常权限结果。无法复验时说明缺口。不要降低安全检查、修改测试期望或删除失败场景来制造绿色。

测试矩阵记录“本次必跑、复用的同条件证据、不适用及理由”；公共接口、依赖锁、迁移、权限/隐私及核心跨模块路径变化须沿依赖扩展验证。独立角色并行通过不能替代最终组合主线的集成检查。验收前重新核对被测提交、构建来源与治理版本；发生新变化不沿用旧 PASS。

## 测试全绿之后检查什么

以原始需求和不变量为准检查测试期望是否正确，尤其是被测实现与测试同时写错的场景。按真实风险选择边界和反例：

- 限额是每条、每批还是整次任务？是否跨循环错误重置？在昂贵分配/处理前还是之后才检查？
- 内存峰值按同时存活的缓冲、容器容量和临时副本计算；阶段被写成互斥时，实际对象是否已经释放？
- 错误、取消、事务回滚后，内存状态、持久化状态与对外成功标志是否一致？部分写入后能否恢复？
- 同 ID 内容被替换、重复/歧义输入、缺失信息是否被错误当作确定结果？
- 合法的不同表示是否保持等价？无关填充/容量/地址变化不能改变业务语义。
- 合成组件测试与真实端到端场景各覆盖什么？小规模演示不能外推到未实测规模、准确率或目标设备。

总控可在自己获准的临时审计目录做最小反例，不修改实现角色拥有的仓库文件。报告写“实际复现”或“代码证据”，避免混淆。独立检查应把需求覆盖到可观察行为，不只再运行同一批测试。

## 补正与遗留

每个问题有 ID、证据、严重程度、责任角色、状态、关闭条件。复审逐项确认旧问题，再检查补正是否引入新问题。原问题与新问题分开归档，保留原提交和追加提交。反复补正时聚焦根因、接口或验收歧义，不无限扩大改动范围；需要跨模块变化先走变更请求。

允许遗留项必须明确“不阻断本任务的理由、影响范围、负责人、最迟关闭的 Part/里程碑”。必需验收未通过不能用遗留项绕过门禁。合成样例、环境受阻、真实效果未验证在后续 review 中持续传递，直到有实际关闭证据。

## 最后一个 Part 不是自动完成

最后一个 Part PASS 后，项目先记 `READY_FOR_ACCEPTANCE`。使用 [项目验收模板](../assets/project-closure.md) 逐项映射项目书需求编号、最终主线提交/发行制品、验证证据、用户操作演示、安装/运行/更新/回退说明、依赖许可证、数据导出/删除及已知限制。非适用项说明原因。

实际执行目标环境或干净环境验证；无法取得第二台设备时如实报告本机可复现验证与未测试平台，不能声称跨设备实测成功。最终验收所需外部部署/发布继续遵守原授权，项目开发授权不等于任意发布授权。

在 `progress/Final/prompt-acceptance.md` 先冻结验收场景，之后写 `review-acceptance.md`。机器部分为 `kind: project`、`decision: PASS`、`prompt`、`primary_commit`、`checks`、`requirements_verified: true`、`blocking_issues: []`、`user_acceptance`（项目内用户验收记录路径）。最终 JSON 只能在事实成立后填写，不能提前把模板 true 当结果。

如果用户事先委托了明确的可客观核验验收方式，记录该授权及执行证据即可；否则等待用户体验确认，并保持 READY_FOR_ACCEPTANCE。用户确认交付且范围内必需项全部通过，再将 STATUS 的 `project_status` 改为 `COMPLETE`、`final_review` 指向最终报告。之后的需求属于新版本变更，不能暗中继续增加 Part 或改写历史成果。
